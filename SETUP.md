# Setup

What each stage needs, how to test it locally, and what to set as
GitHub Actions Secrets before this runs unattended.

## Environment variables by stage

| Variable | Stage(s) | Required? | Notes |
|---|---|---|---|
| `GEMINI_API_KEY` | 1, 2 | No (mock/fail-closed without it) | Used only by Stage 1 (script writing) and Stage 2 (review gate). Without it: Stage 1 emits a mock script, Stage 2 fails closed. Stage 5's stills no longer use Gemini at all - see "Why images come from Pollinations, not Gemini" below. |
| `GEMINI_TEXT_MODEL` | 1, 2 | No | Text model for script writing + review. Default: `gemini-3.6-flash` (verified live against a real key - `gemini-2.5-flash` is deprecated for new users as of this build). |
| `TTS_VOICE` | 3 (voiceover) | No | Edge TTS voice name. Default: `en-IN-NeerjaNeural`. No API key needed. |
| `WHISPER_MODEL_SIZE` | 4 (captions) | No | `tiny` / `base` / `small` / etc. Default: `base`. No API key needed; model weights download on first use. |
| `MOCK_STILLS` | 5 | No | Set to `1`/`true` to force flat placeholder stills instead of calling Pollinations (e.g. for fast/offline testing). Unset by default - Pollinations needs no key, so real stills are the default behavior. |
| `CHARACTER_REF_URL` / `CHARACTER_REF_AUTH_HEADER` | none (optional) | No | **No longer required.** Kept only if you want `fetch_character_reference.py` to pull a local copy for your own reference - no automated stage uses it anymore (see below). |
| `MUSIC_TRACK` | 6 (assembly) | No | Filename (not path) of a track in `assets/music/`. If unset, the first `.mp3` found there is used; if none exist, the final video just uses the voiceover with no music bed. |
| `YOUTUBE_CLIENT_ID` | 7 (upload) | Yes, for upload | OAuth client ID (Desktop app type) from Google Cloud Console. |
| `YOUTUBE_CLIENT_SECRET` | 7 (upload) | Yes, for upload | OAuth client secret, same credential as above. |
| `YOUTUBE_REFRESH_TOKEN` | 7 (upload) | Yes, for upload | Long-lived refresh token for the channel's account (see below for how to mint one). |
| `YOUTUBE_PRIVACY_STATUS` | 7 (upload) | No | `public` / `unlisted` / `private`. Default: `unlisted` (current review-first plan - see "Human-in-the-loop" below). In CI this is a **repo variable**, not a secret (not sensitive). |

Copy [.env.example](.env.example) to `.env` for local testing - `config.py`
loads it automatically via `python-dotenv`. Never commit the real `.env`
(already gitignored).

## Human-in-the-loop architecture: why there's no Veo API key

Earlier builds called Veo 3.1 Lite directly via the Gemini API. That
turned out to be pay-as-you-go billing (~$0.24-0.40 per 8-second clip),
completely separate from the Google AI Pro subscription's 1,000 Flow
credits/month - Flow credits only apply inside the Flow web app, not
the API, and there's no way to call Flow itself programmatically
(no public API for it as of this build).

So the hero clips (`config.HERO_CLIPS_PER_SHORT` = 2 per video) are
generated by a human, manually, in Flow (using already-paid-for Flow
credits, $0 incremental cost), and handed to the pipeline through a
**clip pool**:

1. Each scheduled batch run (`run_pipeline.py --batch`) writes a combined
   brief covering both AM and PM videos to `clip-pool/LATEST_BRIEF.txt`
   for whichever scripts pass review - `<date>-<slot>` is e.g.
   `2026-09-07-AM`.
2. A human runs `show_brief.sh`, pastes each clip's prompt into Flow in
   turn along with the character reference image, generates each clip
   (durations vary per clip - see `HERO_CLIP_DURATIONS_SEC`), downloads
   it, and runs `save_clip.sh <AM|PM> <clip_num>` to save it as
   `clip-pool/incoming/<date>-<slot>-<n>.mp4`.
3. **These files must be `git add`ed, committed, and pushed** - GitHub
   Actions runners don't see your local filesystem, only what's in the
   repo. This is the one manual step; everything else up to this point
   is automatic. A request isn't considered fulfilled until *all* its
   clips are present.
4. The next scheduled run's Stage A (`stageA_clip_pool_watcher.py`)
   finds the complete set, and Stage B (`run_stage_bc.py`) builds the
   video - stills, voiceover, assembly - and STOPS, writing the result
   to `review-pending/<run_id>/final.mp4`. Nothing is uploaded
   automatically, per explicit user decision to keep a human review
   step. This may fulfill a request from several runs earlier, not
   necessarily "today's."
5. A human watches `review-pending/<run_id>/final.mp4`, then runs
   `python scripts/approve_upload.py --run-id <run_id>` (locally, or via
   the manual-only `approve-upload.yml` GitHub Actions workflow) to
   actually publish it. Only on that success are the consumed clips and
   their pending folder deleted automatically. On any failure at any
   step, everything is left untouched so it can be retried.

**Known tradeoff**: `clip-pool/incoming/*.mp4` files get committed to
git history and later deleted by the automation, but git history
retains the blobs indefinitely. Over a long time this will grow the
repo. Periodic history cleanup (e.g. `git filter-repo` or BFG) is a
manual maintenance item, not handled automatically - not urgent, but
worth knowing about.

## Why images come from Pollinations, not Gemini

This took several rounds to get right:

1. First guess: `nano-banana-pro-preview` - wrong, that's the **paid**
   "Nano Banana Pro" tier.
2. Second guess: `gemini-3.1-flash-image` ("Nano Banana 2") - its quota
   error metric was *named* `free_tier_requests`, which looked
   promising, but the error showed `limit: 0` - the free allocation is
   actually zero, so any successful call would have been billed.
3. Third guess, confirmed working by the user at the time:
   `gemini-2.5-flash-image` (original "Nano Banana") - but calling it
   for real got internally routed to `gemini-2.5-flash-preview-image`,
   which *also* showed `limit: 0`. Tested against **two independent,
   never-before-used Google Cloud projects** with fresh API keys - both
   failed identically.
4. **Root cause, confirmed by research**: Google hard-locks the image
   generation quota to `0` on any Google Cloud project without a
   billing account attached - deliberately, as an anti-abuse measure
   against GPU-cluster abuse. This applies to **every** Gemini/Imagen
   image model, regardless of which specific ID you call, region, or
   project age. It is not a bug, not temporary, not fixable by
   switching model names.

**Resolution**: Stage 5 now calls **Pollinations.ai**
(`config.POLLINATIONS_BASE_URL`) instead - no API key, no signup, no
billing, genuinely free, confirmed working. One caveat found during
testing: Pollinations returns `403 Forbidden` for Python's default
`urllib` User-Agent (basic bot detection) - `call_image_api` sends a
browser-like `User-Agent` header to work around this.

**Tradeoff**: Pollinations has no reference-image/image-to-image
support, so stills can't be conditioned on a character reference image
the way a Gemini call would have been - write vivid, specific prompts
in Stage 1 instead of relying on visual conditioning for consistency.

## Character reference - no longer needed by the pipeline

Because (a) stills come from Pollinations (no reference-image support)
and (b) hero clips are generated by you, manually, in Flow - where you
attach the reference image yourself, directly in Flow's UI - **no
automated stage needs programmatic access to the character reference
image anymore.** `CHARACTER_REF_URL` / `CHARACTER_REF_AUTH_HEADER` and
the private-repo hosting setup are no longer required. Keep the
reference image wherever's convenient for your own use when generating
clips in Flow - it doesn't need to be hosted or fetched by any script.

## Visual engine and credit budget

- Video: **Veo 3.1 Lite**, generated manually in Flow (see above) - not
  called via any API by this pipeline.
- Images: **Pollinations.ai** (`flux` model), free, no API key, no
  billing - called by Stage 5. See the note above for why this replaced
  Gemini's image models entirely.

Confirmed, account-verified numbers (do not re-derive these):

- **Google AI Pro** subscription: 1,000 Flow credits/month.
- **~10 credits per 8-second Veo clip** in Flow - this was confirmed for
  Veo generally, not specifically the Lite tier. Verify it still holds
  before trusting the budget math below; update `config.CREDITS_PER_VEO_CLIP`
  if Lite's per-clip cost differs.
- **Chosen structure: `HERO_CLIPS_PER_SHORT` = 2 clips/video** (explicitly
  confirmed, matching the automation report). At 2 clips x 10 credits x
  2 videos/day = **40 credits/day → 1,000/month supports 25 sustained
  days**, then a **~5-6 day pause** each cycle until your Pro renewal.
  This is an accepted tradeoff, not a bug - confirm your actual renewal
  date so a future version of the credit-tracking logic can reset on
  the right day instead of assuming a calendar month.
- Each short is 2 hero clips (≤8s each, from the clip pool) + 3-6
  Pollinations stills, 30-40s total. Stage 2's review gate rejects any
  script that doesn't match this shape, since it bounds how much you're
  asked to manually generate per video.
- **Kling AI** is a possible secondary/overflow engine but is **not
  implemented** - its credit reset cycle (monthly vs. daily) is still
  unconfirmed. Treat it as a future option, not a dependency.
- Run `python scripts/check_credit_budget.py` anytime to see ASSUMED
  Flow credits spent this calendar month against the 1,000 budget (reads
  `cost_logs/usage.csv`, never fails/blocks - informational only).
- **Important**: this pipeline has no visibility into your actual Flow
  usage (it happens in a browser, outside this codebase). Each time
  `run_stage_bc.py` consumes a clip from the pool, it logs an *assumed*
  10-credit spend - a reasonable inference, not a verified figure.
  Cross-check real spend against Flow's own credit display and confirm
  your Pro renewal date so a future version of this tracking can reset
  on the right day rather than assuming a calendar month.

## Watermark and branding placement

Veo leaves a visible "Made with Veo" mark plus an invisible SynthID
watermark on generated clips - Stage 6 does not attempt to cover it
(YouTube's AI-content disclosure requirement makes that redundant
anyway). Confirmed against a real 720p/8s Veo sample clip: the mark is
small white text fixed in the bottom-right corner, static for the whole
clip. The branding overlay in `stage6_assembly.py` (`_overlay_branding`)
is placed top-right for exactly this reason - no further confirmation
needed unless a future Veo version moves its watermark.

## Minting a YouTube refresh token (one-time, done locally)

The Data API needs a refresh token for the channel's Google account.
This is a one-time interactive step you run on your own machine, not
in CI:

1. In Google Cloud Console, create an OAuth 2.0 Client ID of type
   **Desktop app**, and enable the **YouTube Data API v3** on the
   project.
2. Locally, run through `google_auth_oauthlib.flow.InstalledAppFlow`
   with scope `https://www.googleapis.com/auth/youtube.upload`,
   authenticate as the channel's account when the browser opens, and
   print `credentials.refresh_token` at the end.
3. Save the client ID, client secret, and refresh token as GitHub
   Actions Secrets (see below) - the workflow never performs the
   interactive OAuth flow itself.

## GitHub Actions Secrets to set before pushing

Once you push this to a public repo, go to
**Settings → Secrets and variables → Actions** and add:

- `GEMINI_API_KEY`
- `YOUTUBE_CLIENT_ID`
- `YOUTUBE_CLIENT_SECRET`
- `YOUTUBE_REFRESH_TOKEN`

(`CHARACTER_REF_URL` / `CHARACTER_REF_AUTH_HEADER` are no longer needed
- see "Character reference" above.)

The workflow (`.github/workflows/pipeline.yml`) reads all of these
from `secrets.*` - nothing is ever written into the repo itself.

Separately, as a **repo variable** (Settings → Secrets and variables →
Actions → Variables tab, not Secrets - it isn't sensitive): set
`YOUTUBE_PRIVACY_STATUS` to `public` once you're ready to stop
publishing as unlisted.

## Running each stage standalone

Every stage writes its output into `output/<run_id>/`. You can invent
any `run_id` for manual testing.

```bash
# Stage 3: voiceover, from the bundled fixture script - no other stage needed
python scripts/stage3_voiceover.py \
  --script scripts/fixtures/sample_script.json \
  --run-id test1

# Stage 4: captions - NOT part of the automated video pipeline anymore
# (burned-in captions looked clumsy, YouTube auto-generates its own for
# Shorts). Still runnable standalone if ever needed again:
python scripts/stage4_captions.py \
  --audio output/test1/voiceover.mp3 \
  --run-id test1

# Stage 5: still-image generation - calls Pollinations for real by
# default (no key needed). Set MOCK_STILLS=1 to force flat placeholders
# instead. Pass --hero-clip twice for both clips
# (--hero-clip a.mp4 --hero-clip b.mp4); without it, video beats fall
# back to mock placeholders so this stays testable alone.
python scripts/stage5_visual_generation.py \
  --script scripts/fixtures/sample_script.json \
  --run-id test1

# Stage 6: assembly - needs voiceover_meta.json and visuals_meta.json
# from the stage3/stage5 commands above to already exist in output/test1/
# (captions.srt is NOT required - captions aren't burned in anymore)
python scripts/stage6_assembly.py --run-id test1
```

Stage 6 also needs `output/test1/script.json` to exist for reference -
copy the fixture there first if you're testing stages out of order:

```bash
cp scripts/fixtures/sample_script.json output/test1/script.json
```

## Testing the clip-pool handoff (Stages A/B, then review, then upload)

```bash
# Generate today's AM+PM script batch + combined Flow brief
# (writes clip-pool/pending/<date>-AM/ and .../<date>-PM/,
# and clip-pool/LATEST_BRIEF.txt)
python scripts/run_pipeline.py --batch --date 2026-09-07

# Simulate a human having dropped ALL finished Flow clips for AM - a
# request isn't fulfilled until all HERO_CLIPS_PER_SHORT clips are
# present. In real use, scripts/save_clip.py (or save_clip.sh) does
# this for you.
cp /path/to/your/test/clip1.mp4 clip-pool/incoming/2026-09-07-AM-1.mp4
cp /path/to/your/test/clip2.mp4 clip-pool/incoming/2026-09-07-AM-2.mp4
cp /path/to/your/test/clip3.mp4 clip-pool/incoming/2026-09-07-AM-3.mp4

# Run Stage A (just checks - safe to run standalone, exits 0 either way):
python scripts/stageA_clip_pool_watcher.py

# Run Stage A->B (finds the clips, builds the video, STOPS - never
# uploads). Prints the run_id and where to find the built video.
python scripts/run_stage_bc.py

# Watch review-pending/<run_id>/final.mp4. If it's good, publish it -
# this is the ONLY command that ever uploads:
python scripts/approve_upload.py --run-id <run_id>
```

Check `output/<run_id>/report.json` afterward for a per-step record of
what happened during the build - which steps succeeded, which failed
and why, and the assembled video's duration/resolution/size.

If Stage B fails partway, the clips stay in `clip-pool/incoming/` and
the request stays in `clip-pool/pending/` untouched, so re-running
`run_stage_bc.py` retries the same request from scratch. If
`approve_upload.py` fails (bad token, network, quota), the same is
true, and `review-pending/<run_id>/final.mp4` is also kept - nothing is
ever deleted on failure. Only a fully successful upload cleans up the
consumed clip-pool entries and the review-pending entry.

## What each scheduled run actually does

There is no single "run everything" script, both because the hero clip
handoff spans two points in time (AM+PM scripts are generated together
but fulfilled independently) and because uploading is a deliberate,
separate, human-approved step:

```bash
# Morning trigger only: generate + review BOTH today's scripts (AM and
# PM) in one batch, write one combined Flow brief
python scripts/run_pipeline.py --batch --date $(date +%Y-%m-%d)

# Both triggers: check whether ANY previously-requested clip is ready,
# and if so, build it (stills -> voiceover -> assembly) and STOP -
# never uploads
python scripts/run_stage_bc.py

# Separate, manual, only when you're ready to actually publish a video
# you've reviewed - never runs on a schedule:
python scripts/approve_upload.py --run-id <run_id>
```

This is exactly what `.github/workflows/pipeline.yml` runs: the batch
generation step only on the AM trigger, `run_stage_bc.py` on both. It
usually does nothing (exits cleanly, logs "no pending clip") until
you've dropped clips in - that's expected, not a failure.

## Cost/usage tracking

Every stage appends a row to `cost_logs/usage.csv` (tracked in git, not
a secret) recording provider, model, units, and cost per run. Review
this file directly or diff it over time to track spend against budget.
